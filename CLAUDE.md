# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Proof-of-concept for spec-driven development (SDD) using [OpenSpec](https://github.com/Fission-AI/OpenSpec) (CLI v2.0.0, installed globally via npm). The application is a Java 25 / Maven project (`com.pocsdd`), currently just a placeholder `App` with dummy tests.

## Rules (mandatory)

- **Read the OpenSpec before implementing.** Before writing or changing code, read the relevant change in `openspec/changes/<name>/` (`proposal.md`, `design.md`, `tasks.md`, delta `specs/`) and the affected main specs in `openspec/specs/`. Implement what the spec says; if the spec is missing, ambiguous, or wrong, stop and update/clarify the spec first (`openspec-update-change` / `openspec-explore`) instead of improvising.
- **Never change tests to make them pass.** A failing test means the production code is wrong (or the spec changed). Do not weaken assertions, delete, `@Disabled`, skip (`-DskipTests`, `-DskipITs`), or rewrite expected values to match current behavior. A test may only be changed when the spec it encodes has changed — say so explicitly and point to the spec change.
- Do not suppress or relax lint rules (`config/checkstyle/checkstyle.xml`, `-Xlint:all -Werror`) to get a build green; fix the code.
- `./mvnw verify` must pass before a task is considered done.

## Build and test

Java (Temurin JDK 25) and Maven live in `~/.local/opt` (`jdk` and `maven` symlinks); `~/.bashrc` puts the JDK on PATH. If `java` is not found (e.g. a non-interactive shell that skips `.bashrc`), prefix commands with:

```bash
export JAVA_HOME=~/.local/opt/jdk PATH=~/.local/opt/jdk/bin:$PATH
```

Always use the Maven wrapper (`./mvnw`, pinned to Maven 3.9.11).

```bash
./mvnw verify                                  # single command: lint + compile + unit tests + integration tests
./mvnw checkstyle:check                        # lint only
./mvnw test                                    # lint + unit tests only
./mvnw test -Dtest=AppTest#greetsByName        # single unit test (class or class#method)
./mvnw verify -Dtest=skip -Dsurefire.failIfNoSpecifiedTests=false -Dit.test=AppIT   # single integration test
```

How the pipeline is wired (`pom.xml`):
- **Lint**: Checkstyle runs in the `validate` phase (so every build is gated by it), covering main and test sources; any violation fails the build. The compiler also runs with `-Xlint:all -Werror`.
- **Unit tests**: `*Test.java`, run by Surefire in the `test` phase.
- **Integration/functional tests**: `*IT.java`, run by Failsafe in `integration-test`/`verify`. They exercise the application through its entry points (e.g. `AppIT` drives `App.main` and checks stdout).
- Tests use JUnit Jupiter (6.x) and AssertJ. Both test kinds live in `src/test/java`; the class-name suffix decides which plugin runs them.
- `.mvn/jvm.config` silences the JDK 25 `sun.misc.Unsafe` warnings emitted by Maven itself.

## OpenSpec workflow

All feature work is meant to flow through OpenSpec changes, using the `spec-driven` schema (`openspec/config.yaml`):

1. **Propose** (`openspec-propose` skill) — creates `openspec/changes/<name>/` with `proposal.md` (what/why), `specs/<capability>/spec.md` (delta spec), `design.md` (how), and `tasks.md` (implementation steps). Planning only — never edit project code in this step; stop and wait for an explicit request to implement.
2. **Apply** (`openspec-apply-change`) — implement the tasks in `tasks.md`.
3. **Sync** (`openspec-sync-specs`) — merge a change's delta specs into the main specs under `openspec/specs/`, optionally before archiving.
4. **Archive** (`openspec-archive-change`) — finalize a completed change into `openspec/changes/archive/`.

Other skills: `openspec-explore` (think through requirements before/during a change) and `openspec-update-change` (revise a change's planning artifacts; never edits code).

Layout:
- `openspec/specs/` — current source-of-truth specs per capability (empty so far).
- `openspec/changes/` — in-flight changes; `archive/` holds completed ones.
- `openspec/config.yaml` — schema plus optional `context`, per-artifact `rules`, and per-operation `guidance`. Put project constraints that should shape OpenSpec artifacts here rather than in this file.
- `.agents/skills/openspec-*/SKILL.md` — the skill definitions (generated by OpenSpec; regenerate with `openspec update` rather than hand-editing).

Useful CLI commands (the skills drive these; all accept `--json`):

```bash
openspec list --json                         # list changes; "root": null means no openspec/ root
openspec status --change <name> --json       # artifact completion status for a change
openspec show <name>                         # display a change or spec
openspec validate <name>                     # validate a change's artifacts
openspec archive <name>                      # archive a completed change
```
